# Praxeos baseline audit

**Audit date:** 2026-07-14

**Production reviewed:** [praxeos.vercel.app](https://praxeos.vercel.app)
**Scope:** product, learning design, implementation, factual integrity, accessibility, performance, deployment, and repository hygiene

This document records what was directly observed before the flagship upgrade. It deliberately separates confirmed failures from claims that could not be verified and from recommendations. A finding is not marked as passing unless it was actually checked.

## Confirmed failures

### Installation and dependency foundation

- A clean `npm ci` fails against the committed lockfile. npm reports packages required by the dependency graph but missing or invalid in `package-lock.json`, including `@emnapi/runtime@1.11.2` and `@emnapi/core@1.11.2`.
- `next` is pinned to `15.5.15` while `@next/mdx` is declared at `^16.2.4`. The framework and its first-party MDX adapter are on different major versions.
- Because clean installation failed, no baseline build, unit, E2E, or Lighthouse result is recorded as passing in this audit.

### Product and learning design

- The primary information architecture is split across `Learn`, `Cases`, `Modules`, `Glossary`, `Thinkers`, `Manifesto`, and `Colophon`, with no single journey that demonstrates the product promise end to end.
- Eleven lessons are presented on one route, and the case library is presented on one route. Neither surface has focused lesson URLs with resume navigation.
- `ActionAnalyzer` reveals model-answer language in textarea placeholders before the learner attempts an answer.
- The analyzer's completion rule is only that all fields contain non-whitespace text. It does not inspect scenario evidence, concept fit, or key distinctions.
- The successful state unconditionally congratulates the learner. It cannot distinguish a defensible interpretation from filler text.
- The active Calculation Labyrinth is a short simulation, not a persisted seven-step learning journey. Its URL preserves only mode/challenge flags and omits the complete non-sensitive lab state.

### Accessibility and interaction parity

- The Calculation Labyrinth reduced-motion branch returns a static poster instead of an equivalent interactive journey.
- Existing reduced-motion E2E coverage checks for the absence of a canvas and presence of a poster; it does not require equivalent task completion.
- Lighthouse configuration disables `color-contrast` assertions.
- Existing keyboard coverage is limited to the skip link and does not prove the flagship flow can be completed with the keyboard.

### Routes, metadata, and deployment

- The default canonical, robots, sitemap, JSON-LD, Open Graph content, RSS, environment example, and launch material refer to `https://praxeos.org`.
- DNS resolution for `praxeos.org` failed during the audit, while `https://praxeos.vercel.app` was reachable.
- The latest production deployment reported commit `a9659ad`, one commit behind the audited `main` head.
- Lighthouse configuration targets historical module routes, runs once per route, and does not use median results.

### Repository hygiene

- Three module runtimes—`halving-garden`, `time-preference-forest`, and `calculation-problem`—are not present in the active module registry but remain in production source.
- Four private APIs and several scripts/tests support those unreachable runtimes: `/api/blocks`, `/api/m2`, `/api/tile`, `/api/bake-single-block`, tile baking, historical block fetching, and unit coverage for abandoned engines.
- Learning progress, lesson progress, module runs, and pseudo-telemetry use separate local-storage schemas (`praxeos.learning.v1`, `praxeos.progress.v1`, `praxeos.module-runs.v1`, and `praxeos.telemetry.v1`).
- The telemetry queue is local-only and is not a valid substitute for an explicit, consented learner study.

## Unverified claims

- `/built` displays `100/100/100/100` Lighthouse figures as a target/achievement without committed current-route reports that substantiate them.
- Statements suggesting educational effectiveness or human verification are not supported by a completed learner study in the repository.
- Performance, accessibility, best-practices, and SEO thresholds for current production routes are unverified because the baseline clean install failed and current three-run reports are absent.
- Primary-source citations are numerous, but the complete set has not yet been manually verified against stable locators and URLs.

## Factual and source-integrity notes

- The repository contains source lists and thinker material, but there is no shared allowlisted source-packet format for AI feedback.
- No server-side Claude integration exists at baseline. `src/lib/ai/moduleTutor.ts` is a prompt builder, not a provider-backed, cited guide.
- Claims on the future case-study page must distinguish product intent, implementation evidence, measured technical results, and pending educational outcomes.

## Recommendations adopted for the flagship branch

1. Make Calculation Labyrinth a complete 7–10 minute journey with deterministic feedback, refresh persistence, revision, Notebook history, and export.
2. Replace answer-revealing placeholders and non-empty checks with field-specific transparent rubric rules. Do not assign a numeric score.
3. Add a provider-neutral Guide interface with a deterministic no-key provider, allowlisted source packets, native Claude citations, response validation, strict privacy boundaries, and safe rate limiting.
4. Consolidate saved work into one versioned local-first schema with migrations from every current key.
5. Create the target route system (`/learn`, `/practice`, `/journey/calculation-labyrinth`, `/labs`, `/notebook`, `/sources`, `/built`) and permanent compatibility redirects.
6. Align Next and MDX at `16.2.10`, pin Node 22 and npm 10.9.3, regenerate the lockfile, and require clean-install proof.
7. Use `https://praxeos.vercel.app` as the default canonical until the custom domain is registered and attached.
8. Remove unreachable runtimes and private APIs from active source while preserving the decisions and useful design history in Git and `/built`.
9. Restore contrast checks; validate desktop, mobile, keyboard, reduced motion, browser coverage, links, and three-run Lighthouse medians against current routes.
10. Keep the pull request in draft and all educational outcome language marked pending until five real learners complete the protocol and at least one evidence-based revision is committed.

## Release gate

This branch may become a verified portfolio candidate and draft pull request. It must not be merged, tagged `v1.0.0`, or described as educationally validated until:

- five learners have completed the consented protocol;
- anonymized outcomes are reviewed by William;
- at least one revision grounded in that evidence is committed; and
- every required automated and manual check is rerun against the preview and final production deployment.
